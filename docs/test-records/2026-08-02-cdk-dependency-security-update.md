# CDK Dependency Security Update Validation

> **Historical validation record:** The body below describes the repository at the time of this validation and has not been rewritten. Later work removed the source-adjacent generated TypeScript output, resolved the recorded Jest module-resolution warning, and explicitly configured the seven CDK feature flags. See the [TypeScript no-emit and Jest validation](2026-08-02-typescript-noemit-jest-resolution.md) and [CDK feature flag validation](2026-08-02-cdk-feature-flags.md) for the later state.

## Summary

This validation covers a narrowly scoped AWS CDK dependency security update. `aws-cdk-lib` was updated from the previously resolved version `2.245.0` to `2.263.0`, with the `package.json` declaration set to `^2.263.0`.

The AWS CDK Toolkit CLI was updated from `2.1114.1` to `2.1134.0`. The CLI remains pinned to the exact version `2.1134.0` for reproducibility. `constructs` remains resolved at `10.6.0`.

The update addresses CDK dependency vulnerabilities reported by `npm audit` and restores compatibility between the CDK Toolkit CLI and the Cloud Assembly schema generated by the updated library.

A subsequent lockfile-only refresh resolved the remaining development-tooling audit findings without changing `package.json` or any directly declared dependency version. Only `infra/package-lock.json` was updated by this follow-up change.

## Scope

The original CDK dependency update changed only:

- `infra/package.json`
- `infra/package-lock.json`

The subsequent audit remediation changed only `infra/package-lock.json`. Except for this validation record, no application source, Lambda source, tests, README content, CDK stack code, configuration, or feature flags were changed by the follow-up refresh.

The directly declared and resolved versions remained unchanged during the follow-up refresh: `aws-cdk` `2.1134.0`, `aws-cdk-lib` `2.263.0`, `constructs` `10.6.0`, `jest` `30.3.0`, `ts-jest` `29.4.6`, `typescript` `5.9.3`, `ts-node` `10.9.2`, and `@types/node` `24.12.0`.

## Audit Results

Before the update:

- Full audit: four High and one Low vulnerability
- Production audit: three High vulnerabilities

After the original CDK update:

- Full audit: two High and one Low vulnerability
- Production audit: zero reported vulnerabilities

After the subsequent lockfile-only refresh:

- Full audit: zero reported vulnerabilities
- Production audit: zero reported vulnerabilities

The `aws-cdk-lib` advisory was resolved. The production dependency paths involving vulnerable versions of `brace-expansion` and `fast-uri` were also resolved. The updated `aws-cdk-lib` contains `brace-expansion` `5.0.8`, and the unnecessary `table` dependency path that previously included `fast-uri` is no longer present.

The follow-up refresh updated the vulnerable transitive dependencies as follows:

- `@babel/core` `7.29.0` to `7.29.7`
- `brace-expansion` `2.0.3` to `2.1.4`
- The nested `brace-expansion` `1.1.13` to `1.1.18`
- `js-yaml` `3.14.2` to `3.15.1`

The refresh also included coordinated same-major updates to Babel dependencies and browser metadata packages required by the refreshed dependency graph. It did not use `npm audit fix`, an override, or manual `package-lock.json` editing.

Deprecated `glob` 7, `glob` 10, and `inflight` packages remain in the development-tooling dependency graph. These deprecation notices are not current `npm audit` findings. The zero-finding audit results are point-in-time observations and do not establish that the repository or its complete toolchain is free of all vulnerabilities.

## Cloud Assembly Compatibility

The baseline Cloud Assembly used schema `53.0.0`. The updated library generates schema `54.0.0`.

The previous CDK Toolkit CLI `2.1114.1` could not read schema 54 and reported a Cloud Assembly schema mismatch. A limited CLI update to the exact version `2.1134.0` resolved the mismatch.

Development and production synthesis both succeeded with AWS profiles, credentials, container credentials, web identity credentials, and metadata service access disabled. No AWS API or AWS resource operation was performed.

This statement applies to the local synthesis phase. A separately approved development environment validation was subsequently completed as described below.

The lockfile-only refresh was also validated with credential-isolated development and production synthesis. Both syntheses succeeded without an AWS lookup or AWS API call. No deployment was performed for the lockfile-only refresh.

## Security and Cost

The subsequent lockfile-only refresh was entirely local. It did not call an AWS API, deploy a stack, invoke a Lambda function, read or write application data, or change an AWS resource. Its synthesized CloudFormation and IAM output was unchanged, so it introduced no AWS cost change.

The approved development validation called read-only AWS APIs, performed a CDK deployment, invoked the checker Lambda once, and read one DynamoDB item. The deployment updated only the runtime of the existing CDK-managed S3 auto-delete provider Lambda. It did not add, delete, or replace a resource. No production resource was updated, and no resource was destroyed.

The deployment introduced no new continuously billed resource. The single Lambda invocation, keyed DynamoDB read, and log inspection used existing development resources and may incur only normal usage-based AWS charges. Production has no corresponding provider resource because its retained bucket does not use the development auto-delete behavior.
